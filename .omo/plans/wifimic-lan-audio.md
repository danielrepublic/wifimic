# wifimic-lan-audio - Work Plan

## TL;DR (For humans)
<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**What you'll get:** A private project that streams your Linux machine's microphone to your Windows machine's virtual audio cable over the local network, so Discord/OBS on Windows hear the Linux mic. The Linux side stays running quietly all the time but only actually captures audio while the Windows tray app is active; the Windows tray app starts automatically after you log in, and its Restart/Exit menu controls streaming.

**Why this approach:** Rebuild (not copy) the working parts of an existing similar project on the same fixed network port, so the two machines' actual hardware/network limits (confirmed by direct inspection of both machines) are respected, while the capture/streaming lifecycle is redesigned so Linux only listens for a mic when Windows is actually there to receive it.

**What it will NOT do:** It will not encrypt traffic, support more than these two fixed machines, add a second audio codec, run as a hidden Windows background service without your logged-in session, or auto-update itself in the background.

**Effort:** Large
**Risk:** Medium - real two-machine network/audio hardware in the loop (Wi-Fi jitter, VB-CABLE endpoint availability) means some acceptance evidence needs a live run, not just unit tests.
**Decisions to sanity-check:** the 30-second no-heartbeat auto-stop, the 40–200 ms adaptive jitter buffer replacing the old fixed 20 ms buffer, and the P95 ≤ 200 ms application-measured latency target chosen after seeing real Wi-Fi jitter on your network.

## Scope

### Must have
- A new, independent `wifimic` Rust workspace (crates `wifimic_protocol`, `wifimic_diagnostics`; binaries `wifimic_server`, `wifimic_client`) inside a **new private GitHub repository created under the account currently authenticated to the local `gh` CLI** on this Windows host.
- A fixed wire protocol: 48 kHz mono, 16-bit PCM, one bidirectional UDP socket per host on **port 6902** carrying both control messages (start/heartbeat/stop) and audio frames. The existing 484-byte-PCM-frame invariant from the reference project is re-derived and documented (not copied blindly), with a test proving the byte-size math instead of a bare magic number.
- Linux `wifimic-server`: a persistent, always-running user-level systemd service on `arch-daniel` that stays idle until a Windows client is active.
  - Capture is pinned to source name `alsa_input.pci-0000_00_1b.0.analog-stereo` via `parec --channels=1` (mono downmix at the PipeWire level); the server must never silently substitute another source.
  - On a valid client "start" message, the server begins capture/streaming; it stops capture (but the service itself keeps running) after **30 seconds** with no valid client heartbeat.
  - If capture/`parec` fails while a client heartbeat is valid, the server logs a typed error and **retries capture every 5 seconds**, resuming the same session automatically on success; it never falls back to a different or default audio source.
  - The server's UDP socket only accepts control/audio datagrams from the configured Windows peer IP (application-level allow-list) and the host firewall is scoped to that one peer IP and port 6902/udp.
- Windows `wifimic-client`: an interactive Scheduled Task (LogonTrigger + InteractiveToken, i.e. starts after the signed-in user logs in - not a Session-0 service, per confirmed Windows platform constraints) installed to `C:\Program Files\wifimic-client`, with:
  - **Windows artifact naming (canonical, used identically everywhere below):** Scheduled Task `\wifimic\wifimic-client`, Windows Firewall rule DisplayName `wifimic-client`, install directory `C:\Program Files\wifimic-client`.
  - The client's UDP socket only accepts control/audio datagrams from the configured Linux server IP (application-level allow-list, symmetric to the Linux server's) and the host firewall is scoped to that one peer IP and port 6902/udp.
  - A tray icon (hidden by default, visible in the tray) with **Restart** and **Exit** menu items.
  - **Restart**: re-sends a fresh start request/heartbeat stream to the Linux server.
  - **Exit**: immediately sends a stop request and terminates only the current run; the Scheduled Task remains enabled and will auto-start the client again at the next logon.
  - If the Linux server is unreachable (offline, service down, blocked port), the tray process stays alive in the background and **retries the start/heartbeat handshake every 5 seconds**, resuming streaming automatically once reachable - the user never has to click Restart to recover from a transient outage.
  - Audio is rendered via WASAPI to the **VB-Audio Virtual Cable playback endpoint**, which the client enumerates and verifies by exact name at startup (failing clearly, not silently, if the expected endpoint is missing) rather than assuming a fixed display-name direction.
  - An **adaptive jitter buffer**: starts at 40 ms, grows toward a 200 ms ceiling under detected loss/late-frame bursts to protect continuous playback, and decays back toward 40 ms once the network is stable again - replacing the reference project's fixed 20 ms buffer, which real on-network measurement showed is too tight for this Wi-Fi path.
  - Diagnostic logs (no raw audio) rotate under `%LOCALAPPDATA%\wifimic-client`, capped at whichever comes first of 7 days or 10 MiB; Linux diagnostics go to `journald` (systemd's own rotation).
- Deployment: install/update instructions and scripts for both machines that `git clone` (or fetch) from the new private GitHub repository and build locally with the already-present Rust 1.97.1 toolchain on both hosts. Updates are **explicit, manual commands** targeting a specific Git tag or commit; each install/update preserves the last known-good build/config, validates the freshly installed service/client's health, and **automatically rolls back** to the prior good state on failure. There is no background/automatic self-update on either host.
- Verified, application-measured end-to-end audio latency target: **P95 ≤ 200 ms** one-way, measured over the real UDP 6902 path on the actual two-host Wi-Fi network - not inferred from ICMP ping. **Precise measurement boundary (clarified during high-accuracy review, round 4):** the measured origin is the real, pinned capture pipeline's frame-acquisition boundary - the point where audio (a real microphone signal during normal operation) enters wifimic's own software pipeline via `parec`/`CaptureAdapter` (todo 5) - through to the Windows VB-CABLE render boundary (todo 10). This explicitly EXCLUDES any acoustic air-gap/speaker-to-microphone travel time, which is a property of wherever the user physically positions their hardware, not a wifimic software behavior, and is not practically automatable as a zero-human-intervention agent-executed test without dedicated acoustic calibration hardware outside this project's scope. Todo 20's methodology exercises the exact same real PipeWire capture graph node and code path a live microphone signal would use, end-to-end - including PipeWire/`parec`'s own capture buffering, `CaptureAdapter`/`FrameChunker` (todo 5), the protocol/network/jitter-buffer path (todo 3/11/12), and WASAPI render (todo 10) - so all of it is functionally validated as working correctly together. The measured P95 latency NUMBER itself, however, is timed starting at `CaptureAdapter`'s post-acquisition frame timestamp (todo 5), so it does not include whatever time PipeWire/`parec`'s own internal buffering (e.g. the requested `--latency-msec=5` period) took BEFORE that timestamp is recorded - that small, PipeWire-negotiated buffering interval is exercised and implicitly bounded by the `--latency-msec=5` request, but is not itself part of the reported latency figure.
- TDD for all protocol, control-plane, and jitter-buffer logic; agent-executed QA evidence (happy + failure path) for every implementation todo below, plus a final two-host end-to-end verification wave.
- Code quality is deliberately improved over the reference project during this rebuild: explicit state-machine boundaries for the control plane, typed errors (no stringly-typed error handling), small cohesive modules, workspace-wide strict lints (`clippy::all = "deny"`, matching the reference project's own lint bar), and tests that lock in the external behavior decided in this plan - without adding any product capability beyond what is specified here.
- All deployment-facing documentation and instructions are written in Traditional Chinese, per this project's stated session-language convention; source code identifiers/comments use English, matching normal Rust ecosystem convention and the reference project.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- No encryption, authentication infrastructure, Internet/NAT traversal, mDNS/zeroconf discovery, multi-client fan-out, or any general-purpose/configurable networking beyond the two fixed hosts and port 6902.
- No web UI, no VB-CABLE driver bundling/automation (the user installs VB-CABLE manually, as already done).
- No Windows Session-0 service, no separate service+tray-IPC pair, and no pre-logon/unattended audio streaming - the client only runs in the signed-in user's session, per the confirmed Windows platform constraint that Session-0 services cannot host a user-session tray icon.
- No Opus/RTP/WebRTC adoption and no stereo wire-format expansion; the protocol stays 48 kHz mono PCM.
- No automatic/background self-update on either host, and no automatic fallback to a different capture source (Linux) or a different render endpoint (Windows) when the configured one is unavailable - such failures must be logged and retried against the same pinned target, never silently substituted.
- No new product capability beyond `main_draft.md` plus the decisions recorded in `.omo/drafts/wifimic-lan-audio.md`; internal-quality refactors (state machines, typed errors, module boundaries, lints) must not change the external lifecycle/deployment contract agreed in this plan.
