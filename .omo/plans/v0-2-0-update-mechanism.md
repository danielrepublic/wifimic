# v0-2-0-update-mechanism - Work Plan

## TL;DR (For humans)
<!-- Fill this LAST, after the detailed plan below is written, so it summarizes the REAL plan. -->
<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**What you'll get:** On Linux, the existing update-check command gets renamed to match the v0.2.0 naming (behavior unchanged). On Windows, a new double-clickable updater program ships alongside the client: it checks GitHub for the latest release, downloads and verifies it, swaps in the new client automatically, and rolls back cleanly if anything goes wrong — no more needing Git/Rust installed on the end-user's machine. The old developer-only update script is retired, and the release process/deployment docs are rewritten to match.

**Why this approach:** Rebuild the Windows update path on the same "download a verified prebuilt release, atomically swap, roll back on failure" model the Linux side already ships and already tests, instead of the old model that required a full source-code build on the end-user's machine.

**What it will NOT do:** It will not add background/automatic updates on either platform, will not add a `--tag`/version-pinning option to the Windows updater, and will not add any visual "update available" indicator beyond plain console text.

**Effort:** Medium
**Risk:** Medium - the Windows updater touches a real admin-elevation prompt and a real Scheduled Task, which can only be fully proven on the actual two-machine setup, not by unit tests alone.
**Decisions to sanity-check:** if you decline the Windows admin prompt, the update simply doesn't happen (no custom message - just Windows' own cancel dialog); the updater only ever replaces the client program, never itself; and a machine that has never been updated before needs to be reinstalled once (the normal install steps) before the double-click updater is available to use.

## Scope
### Must have
- Rename `apps/wifimic_server`'s `check-update` CLI subcommand to `update` (behavior unchanged; `check-update` becomes `CliParseError::Unrecognized`, no compatibility alias); `upgrade [--tag]` and `doctor` are untouched.
- A new `wifimic_client_updater` binary (explicit Cargo `[[bin]]` target in the existing `apps/wifimic_client` crate) that: downloads the latest public GitHub release archive + SHA-256 checksum manifest, verifies the checksum, safely extracts the ZIP (rejecting path traversal), disables/stops/restores/enables/starts the `\wifimic\wifimic-client` Scheduled Task via `schtasks.exe`, atomically swaps in the new `wifimic_client.exe` (never itself), verifies the VB-CABLE render endpoint is still enumerable and the task reports healthy, and automatically rolls back to the prior working executable + task definition on any failure.
- The updater's side effects live behind an injectable `UpdaterOperations` trait with a `FakeUpdaterOperations` test double (mirroring `apps/wifimic_server`'s `UpgradeOperations`/`FakeUpgradeOperations`), so the core update-flow logic (already-up-to-date / clean success / each failure point's rollback / a rollback-verification failure) is fully unit-tested without touching a real Scheduled Task or filesystem.
- `wifimic_client_updater.exe` carries an embedded `requireAdministrator` UAC manifest bound ONLY to that binary (not to `wifimic_client.exe` or `wifimic_control_smoke.exe`); it accepts zero command-line arguments (no `--tag`); its console prints Traditional-Chinese status text (checking / up to date / updating / success / failure) and waits for a keypress before closing.
- If the user declines the UAC elevation prompt, no state changes anywhere (Windows' own native cancellation dialog is the only feedback; the process never reaches `main()`).
- `install-wifimic-client.ps1` treats `wifimic_client_updater.exe` as a REQUIRED sibling of the client executable during install (hard-fails if missing, unlike the optional `test.md` marker), copies it into `C:\Program Files\wifimic-client\`, and fully covers it in the existing TestMode/DryRun/rollback machinery.
- `.github/workflows/release.yml` builds and packages `wifimic_client_updater.exe` into `wifimic-windows-x86_64.zip` alongside the existing `wifimic_client.exe` and `install-wifimic-client.ps1`.
- `deploy/windows/update-wifimic-client.ps1` (the old git+cargo source-build script) is deleted outright; `docs/release-process.md` §4 and `docs/deployment.md` §1/§7/§12 are rewritten to reference `wifimic_client_updater.exe` instead, including the documented limitation that this step can only verify "latest" (no `--tag` pin, unlike the Linux `upgrade` step) and the one-time bootstrap note that a pre-v0.2.0 machine must rerun the full installer once before the updater exists.
- Every todo below is Implementation + Test in one unit, with agent-executable happy + failure QA evidence; a Final verification wave (F1-F4) runs the mandatory real two-machine verification from `docs/release-process.md` before this work is declared complete.
